## Запуск

Сервер поднимается из каталога `TinyNet.K6Bench` — рабочий каталог обязателен,
`config.json` и `WebRoot` ищутся относительно него:

```bash
cd TinyNet.K6Bench
dotnet run
```

Сценарии запускаются из каталога `loadtests`:

```bash
k6 run baseline.js
k6 run knee-io.js
k6 run -e PROFILE=io    io-vs-block.js
k6 run -e PROFILE=block io-vs-block.js
k6 run -e MODE=clean    errors.js
k6 run -e MODE=oversize errors.js
k6 run -e RATE=110000 -e VUS=1024 -e DURATION=10s saturation.js
```

`saturation.js` — сценарий на полную: `constant-arrival-rate` с фиксированным пулом VU, им
ищется потолок пропускной способности и точка, где начинаются отказы. Ручки `RATE`, `VUS`,
`DURATION` и `TARGET` (по умолчанию `/load/io?ms=0`) задаются через окружение; `NOREUSE=1`
выключает переиспользование соединений и превращает сценарий в шторм новых подключений.

Адрес сервера переопределяется через `-e BASE_URL=http://host:port`.

## Параметры сервера без правки config.json

`Program.cs` читает переменные окружения с префиксом `TINYNET_`, где `__` заменяет `:`.
Регистр имени значим — ключи сравниваются как есть:

```bash
TINYNET_Server__MaxConcurrentRequests=64 dotnet run    # число воркеров
TINYNET_Server__MaxQueuedConnections=256 dotnet run    # ёмкость очереди
TINYNET_Server__MaxBodyBytes=1048576 dotnet run        # лимит тела
```

Приоритет источников: дефолты → `config.json` → переменные окружения, поэтому
переменная всегда перебивает файл.

Сценарию `knee-io.js` те же значения нужно сообщить отдельно, чтобы он посчитал и
напечатал предсказание перед прогоном:

```bash
k6 run -e N=64 -e QUEUE=64 -e MS=1000 knee-io.js
```

## Эндпоинты

| Путь | Что занято на время обработки | Для чего |
|---|---|---|
| `/load/cpu?ms=N` | ядро, поток пула делает реальную работу | насыщение CPU |
| `/load/io?ms=N` | ничего (`Task.Delay`) | обычная форма веб-обработчика |
| `/load/block?ms=N` | поток пула, простаивающий (`Thread.Sleep`) | цена синхронного кода в async-обработчике |

Параметр `ms` обязателен: без него биндинг отвечает 400.

## Что нужно знать до первого прогона

**Открытая модель, а не закрытая.** Все сценарии используют исполнитель `*-arrival-rate`.
Закрытая модель (`constant-vus`) при деградации сервера сама снижает нагрузку и прячет
очередь и перегрузку — ровно то, что мы хотим увидеть.

**Перегруз и пул VU считать от предсказания.** Перегруз должен быть достаточным, чтобы
очередь реально набилась за время ступени, а пула VU должно хватать на **худшую** латентность,
а не на случай без очереди. `knee-io.js` выводит оба числа: перегруз из требования «очередь
набивается за 8 с», VU — из предсказанной худшей латентности. Если в отчёте появились
`dropped_iterations`, подозревать сначала генератор: k6 не выдал обещанную нагрузку.

**Разрешение таймера на Windows.** `med` и `p(90)` будут нулями на быстрых ответах.
Это не «мгновенно», это ниже разрешения измерения. Сравнивать по `p(99)`, `max` и
фактическому RPS.

**Где время сервера.** `http_req_duration` включает установку соединения. Работа самого
сервера — это `http_req_waiting` (TTFB). С keep-alive рукопожатие оплачивается один раз на
соединение, а не на запрос, поэтому две величины теперь близки.

**Пул рабочих считать по соединениям, а не по частоте.** Рабочий владеет соединением всю его
жизнь, поэтому `Server:MaxConcurrentRequests` — это число одновременных клиентов. VU в
прогоне должно быть меньше, чем рабочих, иначе меряется очередь, а не сервер: 1024 VU против
256 рабочих дали 200 rps из предложенных 500 при `p(95) = 22.96 с`, без единого `503` и без
единой записи в логе сервера.

**Эфемерные порты важны только без переиспользования.** С keep-alive соединение несёт до
`Server:KeepAliveMax` запросов, и обычный прогон сжигает мало портов: 10k запросов оставили
22 сокета в TIME_WAIT при `KeepAliveMax=1000` против 12625 с выключенным keep-alive. При
`NOREUSE=1` или при низком `KeepAliveMax` старое ограничение возвращается — каждый запрос
сжигает порт, который потом висит в TIME_WAIT минуты. Диапазон по умолчанию — 16384 порта:

```bash
netsh int ipv4 show dynamicport tcp                       # диапазон
powershell "(Get-NetTCPConnection -State TimeWait).Count"  # сколько занято
```

Такой прогон держать в пределах ~15000 запросов и делать паузы между прогонами, либо расширить
диапазон (нужен администратор, меняет системную настройку до перезагрузки):

```
netsh int ipv4 set dynamicport tcp start=10000 num=55000
```

Если этого не сделать, упрёшься в сетевой стек Windows и примешь его за потолок сервера.

**Генератор и сервер на одной машине.** Для `/load/io` и `/load/block` это приемлемо.
Для `/load/cpu` — искажение: сервер, забравший все ядра, начинает голодать k6.
Архитектурные выводы делать по `io` и `block`.

## Результаты

16 логических ядер, замеры от 17.09.2026 и 18.09.2026.

### Потолок ~90k rps, и отказы начинаются не там

Замеры 18.09.2026 на `/load/io?ms=0` (тело JSON в 23 байта), keep-alive `1000/5`, N = 2048,
очередь 2048, `ReceiveBufferSize` = 4096.

| Предложено | Обслужено | p(95) | `503` | отказы на connect |
|---|---|---|---|---|
| 60 000 | 59 673 | 2.06 мс | 0 | 298 |
| 90 000 | 84 543 | 11.95 мс | 0 | 794 |
| **110 000** | **91 356** | 13.24 мс | 0 | 841 |
| 130 000 | 80 361 | 38.30 мс | 0 | 3 330 |
| 150 000 | 84 287 | 35.76 мс | 0 | 2 914 |

Насыщение около **90k rps**, дальше растёт только задержка. Обрати внимание на столбец
`503`: по установленным соединениям сервер не отказывает, он замедляется. Столбец connect —
это RST, когда тысяча VU дозванивается одновременно в `Listen(1000)`, а не HTTP-ответ. k6
делит машину с сервером и на верхних строках уже не додаёт нагрузку (`dropped_iterations`
дошли до 655k), так что 90k — нижняя оценка сервера, а не его предел.

Отказы определяются **соединениями**, а не частотой. Ёмкость равна
`MaxConcurrentRequests + MaxQueuedConnections`, и её превышение даёт честные `503`:

| Ёмкость | Клиентов | `200` | `503` |
|---|---|---|---|
| 64 + 64 | 512 | 3 648 | 21 341 |
| 256 + 256 | 1 024 | 16 873 | 33 004 |

Из настроек значение имеет только число рабочих, и только через это правило: при 512 VU
варианты 512, 1024 и 2048 дали 59 673 / 59 715 / 59 730 rps. `ReceiveBufferSize` 4096, 8192 и
32768 разошлись в пределах шума (341 / 365 / 344 мкс в среднем).

### Настройки keep-alive: решает таймаут простоя

Одинаковая нагрузка, 256 клиентов на 64 рабочих — режим, где соединений больше, чем слотов:

| `KeepAliveTimeout` | Обслужено | max задержка |
|---|---|---|
| 2 с | 908 rps | 8.89 с |
| 5 с | 500 rps | 16.70 с |
| 15 с | 282 rps | 19.92 с + таймауты у клиента |

`KeepAliveMax` в этом не участвует: при таймауте 2 с значения 100, 1000 и 10000 дали одни и
те же 907 rps. Зато он важен для расхода портов и для потолка — 10k запросов оставили 2588
сокетов в TIME_WAIT при `max=4` против 22 при `max=1000`, а длительный прогон с `max=100`
сжёг 8607 портов за десять секунд и просадил потолок с 91k до 85k rps.

Почему под перегрузкой выигрывает короткий таймаут: соединение, чей клиент уже сдался, всё
равно стоит рабочему полного таймаута, когда до него наконец дойдёт очередь.

### Ёмкость считается по формуле

Предсказание выводится из кода до прогона: потолок пропускной способности равен
`MaxConcurrentRequests`, ожидание в полной очереди —
`MaxQueuedConnections / MaxConcurrentRequests`, а худшая латентность есть это ожидание плюс
собственное время обработчика.

`/load/io?ms=1000`, N = 64, очередь = 64 — предсказанная худшая латентность 2 с:

```
http_req_duration .. med=1.01s  p(95)=1.93s  max=2.02s
status_200 ......... 2395
status_503 .........    6
http_req_failed .... 0.00%
```

Измерено `max = 2.02 с` против предсказанных 2 с. Ёмкость можно планировать по формуле,
а не угадывать, и перегруз даёт честные 503 с ограниченной задержкой.

### Блокирующий обработчик роняет пропускную способность, но не корректность

Одна машина, одна частота (100 rps), одна задержка обработчика (500 мс), N = 256,
очередь = 128. Отличается только способ ожидания.

| | `/load/io` (`Task.Delay`) | `/load/block` (`Thread.Sleep`) |
|---|---|---|
| Успешных | 3001 | 2316 |
| Честных 503 | 0 | 606 |
| Отказов на уровне соединения | 0 | **0** |
| `http_req_failed` | 0.00% | 0.00% |
| Латентность | avg 506 мс, max 535 мс | avg 1.50 с, max 3.48 с |
| Понадобилось VU | 51 | до 228 |

`io` стоит ровно на собственных 500 мс обработчика: 256 воркеров против предложенных
100 rps — очереди нет вовсе.

`block` занимает поток пула на каждый запрос в обработке. Пул стартует с `ProcessorCount`
и доращивает потоки медленно, поэтому фактическая конкурентность держится далеко ниже N,
а очередь набивается. Пропускная способность падает, латентность растёт — этого не избежать,
пока воркеры работают в общем пуле.

Интересно другое — то, чего больше **не** происходит. Поскольку `AcceptLoop` живёт на
собственном потоке (`tinynet-accept`) с блокирующим `Accept()` и синхронной записью `503`,
путь приёма не может быть вытеснен прикладным кодом. Каждый отклонённый запрос получает
настоящий HTTP-статус, который видят и балансировщик, и health-check, и метрика. До этой
правки тот же сценарий давал 1423 отказа на уровне TCP, ни одного 503 и пустой лог сервера.
